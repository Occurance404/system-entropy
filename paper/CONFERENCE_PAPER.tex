\begin{abstract}
Benchmark-level evaluation of tool-using LLM agents is often reported as a single success rate, which obscures two critical factors: infrastructure confounds and observability reliability. We present a confound-aware evaluation protocol and apply it to a workload-scale SWE-PolyBench campaign of 500 task-runs (100 tasks for each of five models). Across all rows, aggregate success is 34/500 (0.068), but this view is materially confounded by infrastructure-prefetch failures (115 runs total, including one model with 0.95 infra-failure rate). After excluding infrastructure-prefetch rows, the clean non-infrastructure slice contains 385 runs with success 34/385 (0.088), changing cross-model interpretation. We report branching-probe instability via SCR\_probe together with probe-log coverage and backend mode disclosure. For the completed campaign in this paper, SCR\_probe was computed under a deterministic lexical-hash fallback backend and is therefore reported as a proxy instability signal. We complement aggregate outcomes with failure forensics, showing concentrated failure mass in specific categories and repository families rather than diffuse random error. The result is a reproducible reporting framework for workload-scale agent evaluation that separates operational reliability from agent behavior.
\end{abstract}

\section{Introduction}
The rapid adoption of LLM-based agents for autonomous software engineering~\cite{yao2023react,schick2023toolformer,xi2023rise} has highlighted a critical reliability gap. While agents perform well on static benchmarks~\cite{jimenez2024swebench,chen2021codex}, their performance degrades significantly in long-horizon tasks with changing requirements~\cite{Chen2024ToolsFail,Guo2024Defects}. This degradation is often characterized not by immediate failure, but by a gradual ``Context Rot,'' where the agent's internal state drifts from the ground truth~\cite{liu2023lost,Wang2025ComplexityTrap}, leading to repetitive loops and hallucinated progress~\cite{huang2024selfcorrect,ji2023hallucination}.

Standard benchmark reporting often conflates three distinct phenomena: agent behavior, infrastructure reliability, and metric availability. In practice, missing observability channels (for example, unavailable token logprobs~\cite{Chen2025Overconfidence,Tian2023Calibration}) and pre-execution infrastructure failures~\cite{Tang2025Empirical,Patel2025InferenceReliability} can dominate measured outcomes if not explicitly separated. Recent work has shown that even widely used benchmarks like SWE-bench suffer from solution leakage and weak test coverage~\cite{Aleithan2024SWEBenchPlus,Wang2025SavingSWE,yang2024swebenchplus}, while evaluation harness design itself introduces confounds such as prompt sensitivity~\cite{Biderman2024LMEvalHarness}, further motivating careful reporting methodology.

This paper contributes:
\begin{enumerate}
  \item \textbf{A confound-aware reporting protocol} that separates all-row operational outcomes from a clean non-infrastructure slice for behavior-focused interpretation.
  \item \textbf{A workload-scale benchmark execution} on SWE-PolyBench with fixed budgets, chunked resumability, and deterministic artifact generation.
  \item \textbf{An observability reporting rule for SCR\_probe}: report instability values jointly with probe coverage and backend mode (semantic vs proxy), and avoid comparative claims under low coverage.
  \item \textbf{Failure forensics at benchmark scale}, showing concentrated failure categories and repository-level hotspots that guide targeted follow-up analysis.
\end{enumerate}

\section{Experiments}

\subsection{Campaign Configuration}
The reported campaign evaluates the following model endpoints under a common harness configuration: \texttt{moonshotai/kimi-k2.5}, \texttt{deepseek/deepseek-v3.2}, \texttt{z-ai/glm-4.7}, \texttt{openai/gpt-5-mini}, and \texttt{google/gemini-3-flash-preview}. All models are run on the same 100-task SWE-PolyBench sample with identical step budget and probe settings.

\subsection{Inclusion, Exclusion, and Evidence Scope}
Primary claims in this paper are derived from the completed five-model campaign (\texttt{20260225\_231718}) and its associated closeout/forensics artifacts. Earlier interrupted or partial campaigns were used only for protocol debugging and are not used for headline comparative claims. We additionally report one post-hoc replacement run for \texttt{z-ai/glm-5} (\texttt{20260305\_020845\_glm5}) on the same 100-task sample as a follow-up point estimate, not as a synchronized five-way campaign comparison.

\subsection{Observability Backend Disclosure}
For run \texttt{20260225\_231718}, SentenceTransformer weights~\cite{reimers2019sentencebert} were unavailable at run time; therefore SCR\_probe was produced by the lexical-hash fallback backend. We explicitly report these values as SCR proxy in both main text and appendix. This disclosure is treated as part of the experimental condition rather than hidden implementation detail.

\section{Results}

\subsection{Workload Outcomes Require Confound-Aware Reporting}
The primary campaign (\texttt{20260225\_231718}) contains 500 runs (100 per model). In the all-row operational view, success is 34/500 (0.068). Model-level rates are 0.140 (Gemini), 0.120 (Kimi), 0.050 (DeepSeek), 0.030 (GPT-5-mini), and 0.000 (GLM-4.7).

The key issue is confounding, not just ranking. Infrastructure-prefetch failures are highly asymmetric: DeepSeek 0.20 and GLM-4.7 0.95, while the other models are 0.00. When these rows are removed, the clean non-infrastructure slice has 385 runs with success 34/385 (0.088). DeepSeek shifts from 5/100 (0.050) to 5/80 (0.062), and GLM-4.7 is left with only 5 interpretable non-infrastructure rows. This is the central empirical point: behavior claims should be based on the clean slice, with the all-row view retained for operational reliability~\cite{Wang2025SavingSWE,Wang2025DissectingSWE}. Supporting evidence is in Table~\ref{tab:app-all-rows}, Table~\ref{tab:app-clean-rows}, and Figure~\ref{fig:app-workload-panels}--Figure~\ref{fig:app-failure-panels}.

\subsection{SCR\_probe Is Useful Only with Explicit Coverage}
Probe coverage varies enough to change interpretation. Probe-log coverage is 0.94 (GPT-5-mini), 0.90 (Kimi), 0.90 (Gemini), 0.76 (DeepSeek), and 0.02 (GLM-4.7). Median per-run SCR\_probe medians are 0.444, 0.475, 0.325, 0.371, and 0.445, respectively.

Two constraints apply. First, GLM-4.7 has only two probe-covered runs, so its SCR\_probe value is not suitable for model-to-model comparison. Second, this campaign used lexical-hash fallback embeddings, so reported values are SCR proxy rather than semantic embedding divergence~\cite{Zhou2024Consistency,reimers2019sentencebert}. The reporting rule is therefore coverage + backend disclosure + cautious comparison. Probe evidence is in Table~\ref{tab:app-probe} and Figure~\ref{fig:app-probe-panels}.

\subsection{Failure Forensics Show Structured Failure Modes}
Failure mass is concentrated in a few categories. The largest is \texttt{agent\_executed\_other\_failure} (295/466 failed runs, 63.3\%), followed by \texttt{infra\_dns\_mirror\_fetch} (115/466, 24.7\%) and \texttt{test\_failure} (22/466, 4.7\%). These concentrated failure profiles echo findings in multi-agent failure taxonomies~\cite{tyen2024mast,zhang2024systemfailures}, where a small number of failure modes dominate overall failure mass.

Concentration is also repository-specific in non-infrastructure failures: huggingface/transformers (65), mui/material-ui (60), and serverless/serverless (48). This gives a concrete remediation strategy: optimize against the highest-mass categories and repositories first. Evidence appears in Table~\ref{tab:app-fail-cats}, Table~\ref{tab:app-fail-repos}, Figure~\ref{fig:app-forensics-categories}, and Figure~\ref{fig:app-forensics-structure}.

\subsection{GLM-5 Follow-Up Run on the Same Task Sample}
Because GLM-4.7 was dominated by infrastructure failures, we ran a GLM-family follow-up with \texttt{z-ai/glm-5} on the same 100-task sample (\texttt{20260305\_020845\_glm5}). GLM-5 achieves success rate 0.14 (14/100), infra-prefetch failure rate 0.00, and zero-step rate 0.11. Median total tokens including probes are 520{,}435, with 0.287 successes per million tokens.

As a point estimate, GLM-5 matches Gemini's 0.14 success rate while using fewer median tokens (562{,}154 to 520{,}435), and exceeds Kimi's 0.12 success rate on the same sample. We treat this as follow-up evidence, not a synchronized five-model leaderboard replacement. Details are in Table~\ref{tab:app-glm5-followup} and Figure~\ref{fig:app-glm5-workload}.

\section{Related Work}

\textbf{Benchmark evaluation for tool-using agents.}
Static benchmarks such as SWE-bench~\cite{jimenez2024swebench} and HumanEval~\cite{chen2021codex} have been instrumental in measuring agent code-generation ability, but recent critiques reveal significant confounds: Aleithan et al.~\cite{Aleithan2024SWEBenchPlus} found 32.67\% solution leakage and 31.08\% weak tests in SWE-bench, while Wang et al.~\cite{Wang2025SavingSWE} proposed benchmark mutation to mitigate these issues. UTBoost~\cite{wei2024utboost} further showed that manually written test cases are often insufficient for rigorous evaluation, while Wang et al.~\cite{Wang2025DissectingSWE} profiled submitter architectures and found substantial variance in how agents approach the same tasks. Stateful, multi-turn benchmarks such as ToolSandbox~\cite{Zhou2024ToolSandbox}, $\tau$-bench~\cite{Fu2024Tau}, and MCPMark~\cite{Grattafiori2025MCPMark} have introduced richer evaluation protocols, and recent efforts like the Holistic Agent Leaderboard~\cite{Doris2025HAL} have begun reporting Pareto frontiers of accuracy versus cost. However, none of these explicitly separate infrastructure confounds from agent behavior in their reporting. Li et al.~\cite{Li2024SWEAgent} demonstrated that agent-computer interface design critically impacts measured performance, further motivating confound-aware reporting.

\textbf{Observability and uncertainty for LLM reasoning.}
Token-level entropy has been the default confidence proxy for language models~\cite{holtzman2020curious,shannon1948mathematical}, but RLHF fine-tuning decouples surface confidence from actual uncertainty~\cite{Chen2025Overconfidence,Tian2023Calibration,ouyang2022training}. Perez et al.~\cite{Perez2024Mislead} showed that RLHF-trained models learn to produce persuasive-but-incorrect outputs, while Wang et al.~\cite{Wang2024StyleOutweighs} found that reward models prioritize style over substance. Consistency-based uncertainty quantification, where multiple sampled responses are compared in embedding space~\cite{reimers2019sentencebert}, has been shown to outperform pointwise calibration methods~\cite{Zhou2024Consistency}. Conformal prediction provides distribution-free foundations for such approaches~\cite{Barber2022ConformalPrediction,Vovk2025Conformal}. Our branching-probe protocol operationalizes this line of work as a per-step diagnostic within a benchmark harness.

\textbf{Software-engineering task suites with deterministic validators.}
The shift toward deterministic validation in agent benchmarks reflects growing concern about evaluator reliability~\cite{wei2024utboost,Hu2025RevisitingSWE}. Chen et al.~\cite{Chen2023ToolEmu} found that 68.8\% of simulated sandbox failures would occur in real-world tool use, motivating execution-based evaluation. Agent failure taxonomies~\cite{tyen2024mast,zhang2024systemfailures,Guo2024Defects} have documented concentrated failure modes in multi-agent and single-agent systems alike, while Jiang et al.~\cite{Jiang2025DarkPatterns} highlighted agents' vulnerability to manipulative GUI patterns. Our framework builds on these insights by combining deterministic validators with explicit confound separation and probe-level observability, yielding an evaluation protocol that preserves behavioral interpretability under operational noise.\looseness=-1

\section{Discussion \& Future Work}
The main practical finding is methodological rather than leaderboard-oriented: all-row benchmark outcomes can materially misrepresent agent behavior when infrastructure-prefetch failures are not separated. The clean non-infrastructure slice changes interpretation and should be treated as a required companion view for cross-model discussion.

This campaign also highlights three limitations. First, SCR\_probe was reported in proxy mode (lexical-hash backend) rather than semantic embedding mode~\cite{reimers2019sentencebert}. Second, probe coverage is asymmetric across models, which weakens direct SCR comparisons for low-coverage cases. Third, token-cost comparisons remain sensitive to provider accounting and should be interpreted as workload-relative rather than absolute efficiency claims. These operational-level confounds mirror patterns documented at cloud scale, where Patel et al.~\cite{Patel2025InferenceReliability} found that 60\% of production LLM inference incidents are engine failures and 40\% of those are timeouts, and Agarwal et al.~\cite{Agarwal2025FAILS} developed systematic frameworks for LLM incident collection and analysis.

\textbf{Future work includes:}
\begin{enumerate}
  \item \textbf{Semantic-SCR rerun:} regenerate the campaign with cached SentenceTransformer embeddings~\cite{reimers2019sentencebert} to replace proxy SCR with semantic SCR.
  \item \textbf{Coverage-aware uncertainty reporting:} add bootstrap intervals for success-rate deltas and SCR summaries on matched coverage subsets~\cite{Barber2022ConformalPrediction}.
  \item \textbf{Targeted failure remediation:} run focused follow-ups on high-mass failure categories and top non-infrastructure repositories.
\end{enumerate}

\section{Conclusion}
We presented a confound-aware evaluation framework for workload-scale SWE agent benchmarking and applied it to a completed five-model campaign. The central result is that operational confounds and observability conditions must be explicitly reported to preserve valid behavioral interpretation. By separating all-row and clean non-infrastructure outcomes, disclosing SCR backend mode, and providing failure forensics, the framework yields a more defensible evidence chain than single-metric leaderboard reporting.
